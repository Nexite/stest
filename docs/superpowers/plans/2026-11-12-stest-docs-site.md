# stest Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user-facing documentation website for stest (MkDocs Material on GitHub Pages, API reference from docstrings), plus a supported, CI-tested way to use stest from another repository with an example project the guides are built on.

**Architecture:** stest's CMake gains an out-of-tree mode (`add_subdirectory` from a consumer project, self-tests off). `examples/sensor-node/` is a standalone consumer project (two firmware boards + pytest tests) that CI configures from its own directory. The site is built from `docs/` (internal `superpowers/` and `spikes/` excluded); guides pull code from the example's real files with snippet includes, and the API reference is generated by mkdocstrings from the package's docstrings.

**Tech Stack:** CMake ≥ 3.23, upstream LLVM ≥ 18, Python ≥ 3.11 + uv, MkDocs + mkdocs-material + mkdocstrings[python] (Google-style docstrings), pymdown-extensions (snippets, admonitions, tabs), GitHub Actions + GitHub Pages.

**Spec:** `docs/superpowers/specs/2026-11-12-stest-docs-site-design.md` (approved 2026-11-12). Read it; it holds the site outline and the settled calls this plan argues from.

## Global Constraints

- No simulator behaviour or Python API changes beyond docstrings and the out-of-tree CMake option; missing features found while writing go to `docs/superpowers/plans/2026-11-12-docs-site-followups.md`, not into code.
- No first-user-project names, pins, boards or DBC contents anywhere (site, example, tests). The example is generic.
- Every shell/CMake command on the getting-started path is one CI runs (example job or docs job). Anything not run by CI is labelled "not tested by CI" in the page.
- One source of truth per fact: an option or env var is described on one page; others link to it.
- Generated API reference = public API only: `stest` top-level `__all__` and `stest.can` public classes. No `protocol`, `symbols`, `macho`, private (`_`) members.
- Docs build: `uv run --group docs mkdocs build --strict` must pass; it needs Python only (no C toolchain).
- Docs tooling is permissively licensed (MkDocs BSD-2, mkdocs-material MIT, mkdocstrings ISC, pymdown-extensions MIT).
- `site_url: https://nexite.github.io/stest/`; deploy only from `main` via `actions/upload-pages-artifact` + `actions/deploy-pages` (`github-pages` environment). Pages is enabled by the repo owner (Settings → Pages → Source: GitHub Actions); the workflow must not fail PR builds when Pages is not enabled (deploy job runs only on `main`).
- Default HAL = stest's pinned, fetched ST HAL; consumers list only their own `Core/` sources and `Core/Inc`. `STEST_STM32L4_HAL_DIR` is documented as "not tested by CI".
- Primary consumption pattern = stest as a git submodule (a path) + `add_subdirectory`; Python via a uv path dependency on that checkout. FetchContent is not documented; git-URL install gets one line labelled untested.
- Existing repo rules (AGENTS.md) hold: every CTest has a TIMEOUT; change-together lists; commit trailers.
- Platforms: macOS arm64 native, Linux (Docker image `docker/`) in CI.

## Review Focus

1. **Consumer with its own `enable_testing()`**: a user expects `ctest` in their build to list only their tests, not stest's 44. → Task 1 test asserts `ctest -N` in a consumer lists no `runtime_`/`chip_`/`selftest_`/`python_` tests.
2. **Toolchain include forgotten / placed after `project()`**: a user who writes a plain `project()` first gets Apple clang or gcc; they expect an error naming the fix, not a cryptic compile failure. → Task 1 test configures a consumer without the include and asserts the configure fails with a message containing `StestToolchain.cmake` and `before project()`.
3. **Two boards in one consumer** (multi-board projects are the main use): both `stest_add_firmware` targets with the same CHIP must build and run side by side. → Task 2 builds two firmware targets and a test runs both on one bus.
4. **Moved/excluded links**: `docs/can.md` and `docs/adding-a-*.md` link to `superpowers/` and `spikes/` files that the site excludes; strict mode must not break and the links must still work. → Task 3 rewrites such links to absolute GitHub URLs and the strict build is the test.
5. **Fresh environment without stest's dev group**: the example's tests must run from a clean `uv sync` in the example directory (path dependency + `dbc` extra), not from stest's own venv. → Task 2's CI job runs `uv sync` / `uv run pytest` inside `examples/sensor-node` with `UV_PROJECT_ENVIRONMENT` unset.

**Files:**
- Modify: `CMakeLists.txt`, `cmake/StestToolchain.cmake`, `cmake/StestFetchST.cmake:94`, `runtime/CMakeLists.txt:17,76`, `chips/stm32l4/CMakeLists.txt:9-44`, `selftest/CMakeLists.txt` (all `${PROJECT_SOURCE_DIR}` / `${CMAKE_BINARY_DIR}` uses)
- Create: `selftest/check_out_of_tree.cmake`, `selftest/out_of_tree/ok/CMakeLists.txt`, `selftest/out_of_tree/no_toolchain/CMakeLists.txt`
- Modify: `selftest/CMakeLists.txt` (register the new tests), `AGENTS.md` (Setup section, change-together)

**Interfaces:**
- Produces: cache option `STEST_BUILD_TESTS` (BOOL, default `${PROJECT_IS_TOP_LEVEL}` evaluated for the stest project); variable `STEST_ROOT_DIR` (stest's source root, set in the top `CMakeLists.txt` with `CACHE INTERNAL`); consumer contract:
  ```cmake
  cmake_minimum_required(VERSION 3.23)
  include(<stest>/cmake/StestToolchain.cmake)   # before project()
  project(my_sil C CXX)
  add_subdirectory(<stest> stest)
  stest_add_firmware(board_a CHIP STM32L496RG SOURCES ... INCLUDE_DIRS ...)
  ```
- When `STEST_BUILD_TESTS` is OFF: `spike/` and `selftest/` are not added, and `runtime/`/`chips/` skip their test executables and `add_test` calls; `stest_add_firmware` and the runtime/chip libraries work unchanged.

For `CASE=no_toolchain`: configure fails and the collapsed-whitespace output contains `StestToolchain.cmake` and `before project()`. - Produces (used by Tasks 5–6 as snippet sources — keep these paths stable):

  - CMake targets `sensor` and `display` built by `stest_add_firmware` (default HAL, `Core/` sources only).
  - `pyproject.toml`: `dependencies = ["stest[dbc]"]`, `[tool.uv.sources] stest = { path = "../..", editable = true }`, pytest dev group.
